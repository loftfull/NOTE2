# NOTE2 — Implementation Plan

## Rule zero

Do not begin a wide refactor until the full project mirror is present in NOTE2 and one of these gates is green:

- hosted GitHub CI; or
- `npm run ci:local` Docker gate.

The current system already contains working upload, storage, worker, database, auth, search and PWA/Android hardening. The goal is to evolve these pieces, not replace them.

## Stage 0 — repository consolidation

### Required

1. Run the full mirror script from `NOTE2/main` on a machine authenticated to GitHub:
   - Windows: `powershell -ExecutionPolicy Bypass -File scripts/migrate-full-history.ps1`
   - macOS/Linux: `bash scripts/migrate-full-history.sh`
2. Confirm these source refs exist in NOTE2 after mirror:
   - `claude/shadow-knowledge-ai-OgOPz`;
   - `chatgpt/resumable-mobile-hardening`;
   - `chatgpt/mobile-pwa-shell`.
3. Recreate/retarget the two draft PRs inside NOTE2.
4. Run CI/local gate.
5. Only after green checks consolidate into the new NOTE2 working branch.

### Do not

- copy only `/src` and forget migrations/scripts/docs;
- squash away history before hardening/mobile changes are validated;
- merge the PWA stack before backend hardening is accepted;
- rename database models as part of repository migration.

## Stage 1 — establish universal `Source` domain without schema rename

Current code is centered on `MediaFile`. Do not rename it immediately.

Introduce a domain service layer:

```text
src/domain/source/
  types.ts
  source-service.ts
  adapter-registry.ts
  provenance.ts
  errors.ts
```

`MediaFile` remains the persistence model initially. The service exposes the future `Source` vocabulary to new code.

### First interfaces

```ts
SourceInput
SourceDescriptor
SourceAdapter
SourceRepresentation
SourceAnchor
SourceFailure
```

All new ingestion features use these interfaces.

## Stage 2 — adapter registry around existing pipelines

Wrap existing behavior before adding new source types.

Order:

1. local upload/file;
2. YouTube;
3. web/Readability;
4. PDF;
5. office documents;
6. audio/video normalized extraction;
7. image;
8. Instagram/social.

For each adapter:
- use existing implementation internally first;
- add conformance tests;
- remove route-level duplication only after tests pass.

### Registry

```ts
const adapters: SourceAdapter[] = [
  localFileAdapter,
  youtubeAdapter,
  webArticleAdapter,
  pdfAdapter,
];
```

Routes call registry, never import downloader/parser SDKs directly.

## Stage 3 — representation cache

Before building more analysis modes, make extraction reusable.

Add metadata sufficient to answer:

```text
Do we already have a transcript/text/frame-set generated by the same extractor/version/parameters?
```

Prefer an additive table/model over modifying large existing payload columns.

Minimum fields:
- source/media id;
- representation type;
- extractor/provider;
- version;
- parameters hash;
- artifact/storage reference;
- coverage;
- metadata;
- timestamps.

Do not move large transcripts into Postgres JSON if object storage is already the better artifact location.

## Stage 4 — anchors and evidence

Normalize location references before claim verification.

Common `SourceAnchor` union:

```ts
type SourceAnchor =
  | { kind: "time"; startMs: number; endMs?: number }
  | { kind: "page"; page: number; paragraph?: number; bbox?: BBox }
  | { kind: "web"; url: string; headingPath?: string[]; paragraph?: number }
  | { kind: "image"; bbox: BBox };
```

Existing chunks/transcript segments should be mapped into this type through service code first.

## Stage 5 — multi-mode analysis runs

Current `MediaAnalysis` remains operational. Add versioning fields or adjacent run records incrementally.

Target behavior:

```text
source
 ├─ QUICK
 ├─ FULL
 ├─ SIMPLE
 ├─ EXPANDED
 └─ VERIFIED
```

All runs share representations.

### Planner

Create an analysis planner separate from workers:

```text
requested mode
  ↓
required graph nodes
  ↓
reuse available nodes
  ↓
queue only missing nodes
```

Workers execute nodes; they do not decide product strategy.

## Stage 6 — claims and verification

Introduce claim extraction only after anchors exist.

Claim model requirements:
- normalized text;
- type;
- confidence;
- verification status;
- source analysis run;
- many-to-many evidence links.

External verification is another node, not embedded inside the first summarization prompt.

## Stage 7 — Result Workspace UI

Build the result UI against adapter/analysis APIs, not legacy route shapes.

### Mobile first

Implement in this order:

1. compact source header;
2. overview list;
3. mode switcher;
4. evidence bottom sheet;
5. timeline/pages tab;
6. verification view;
7. entities;
8. related;
9. Ask NOTE2;
10. desktop split pane.

Avoid a full redesign of unrelated settings/dashboard screens during this stage.

## Stage 8 — Compare

Only after single-source evidence is stable.

Compare input:
- 2–N sources;
- optionally selected sections/claims.

Compare works over normalized claims/evidence and retrieves raw segments only when needed.

## Stage 9 — Android release

The PWA/TWA work already exists in the hardening stack.

After NOTE2 deployment has a stable HTTPS origin:

1. run hosted preflight;
2. validate PWA;
3. initialize Bubblewrap workspace;
4. run doctor/API 36 checks;
5. build unsigned APK;
6. sign with isolated `apksigner`;
7. configure SHA-256 in Digital Asset Links;
8. verify site;
9. device smoke test.

Do not create a second native backend or duplicate web screens in Android.

## Stage 10 — provider routing and cost intelligence

Only after graph nodes expose metrics.

Record per node:
- provider;
- model;
- latency;
- input/output tokens;
- estimated cost;
- retry count;
- quality/evaluation score when available.

Then route based on evidence rather than vendor preference.

Possible routing pattern:

```text
cheap deterministic extraction
  → mid-cost classification
  → strong synthesis model
  → external verification only for selected claims
```

## QA strategy

Every stage must add one of:
- contract tests;
- integration tests;
- production smoke checks;
- browser/device acceptance tests.

No stage is complete because “the code compiles”.

### Mandatory regression scenarios

- 500 MiB upload interrupted and resumed;
- Redis unavailable after object storage commit;
- DB retry after multipart completion;
- YouTube acquisition unavailable but metadata still preserved;
- partially accessible source reports coverage <100%;
- SIMPLE mode reuses transcript from FULL;
- VERIFIED adds verification nodes without re-upload;
- claim opens exact timestamp/page;
- logout never reveals cached previous-user content;
- Android DAL endpoint remains public while dashboard remains protected.

## Architecture review checklist

Before adopting any OSS library/repository:

1. Which existing NOTE2 subsystem does it improve?
2. Does it replace or duplicate something?
3. Is it actively maintained?
4. Is its license acceptable?
5. Can it run behind an adapter?
6. What happens when it fails or disappears?
7. How is it tested independently?
8. What is the removal path?

If answers 2, 5 or 6 are unclear, do not merge it.

## First code change after migration

The first implementation PR after repository consolidation should be intentionally small:

**“Introduce SourceAdapter registry around existing local-file and YouTube ingestion without changing persistence schema.”**

Acceptance criteria:
- current upload and YouTube behavior unchanged;
- routes no longer own source detection;
- two adapters pass the same contract suite;
- typed failure taxonomy introduced;
- no new provider or downloader dependency;
- CI + smoke green.

This is the safest bridge from the current application to the universal analyzer architecture.
