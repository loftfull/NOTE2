### P0-3 — Локальная эвристика выдаётся за ответ модели (нарушение fail-closed)

| | |
|---|---|
| **Severity** | P0 |
| **File** | `src/ai.js:91–105` (`runAiTask`) |
| **Symptom** | При недоступном шлюзе пользователь получает текст, неотличимый от ответа AI. |
| **Root cause** | `catch { return localFallback({ action, input }) }` — «голый» catch без привязки к типу ошибки. Он поглощает *всё*: сетевой сбой, не-2xx, HTML вместо JSON, некорректный JSON. Возвращается строка того же типа, что и успешный ответ; у вызывающего кода нет ни флага, ни поля, чтобы отличить одно от другого. |
| **User impact** | Самое опасное — ветки `source-brief` и `grounded-analysis`: они возвращают текст **с цитатами вида `[S1]`**, собранными регуляркой. Пользователь видит оформленный, «подкреплённый источниками» ответ, который модель никогда не порождала. Это сфабрикованная provenance. |
| **Evidence** | `runAiTask` возвращает `localFallback(...)` и при `!endpoint`, и в `catch`. Ветки `instagram-*` честно помечены «(локально)», а `summarize`, `keywords`, `improve`, `title`, `source-brief`, `grounded-analysis` — **не помечены ничем**. |
| **Fix** | Возвращать размеченный результат (`{ text, origin: 'model' \| 'local', error }`) и при настроенном, но упавшем endpoint — не подменять ответ, а поднимать ошибку. Локальный режим допустим только как явный выбор пользователя и только с видимой пометкой в UI. |
| **Regression test** | При заданном endpoint и ответе 500 / `text/html` / битом JSON — `runAiTask` обязан отклониться, а не вернуть эвристику. |

## C. ARCHITECTURE REVIEW

Оценка возможна только по 48 восстановленным файлам; это не весь проект.

**God component подтверждён.** `src/App.jsx` — 1088 строк, но 152 870 байт, то
есть в среднем ~140 символов на строку: код сжат в сверхдлинные строки. Для
сравнения, следующий по размеру модуль (`archive-text.js`) — 199 строк. App.jsx
держит настройки, аккаунт, синхронизацию, импорт/экспорт, редактор, просмотр
источников и весь UI одновременно.

**Дублирование логики с расхождением поведения.** `gatewayApiEndpointFor` и
`healthEndpointFor` существуют дважды: в `gateway-url.js` (с параметром
`baseHref`, пригодны для тестов) и внутри `App.jsx` (жёстко прибиты к
`window.location.href`). Это не просто копипаста — это ровно тот дефект, который
и ломает сборку (P0-2). Показательно: тест может проверять версию из
`gateway-url.js` и быть зелёным, тогда как приложение использовало бы копию из
`App.jsx`.

**Смешение ответственностей клиента и сервера.** `sync-core.mjs`,
`account-auth-core.mjs`, `instagram-core.mjs`, `media-connectors.mjs` лежат в
корне рядом с клиентским `src/`, без разделения на пакеты. Границу
клиент/сервер приходится держать в голове.

**Что сделано хорошо** (говорю прямо, раз так и есть):
`src/api-session.js` привязывает `Authorization` к origin
(`target.origin === apiSession.origin`) и не прикрепляет токен к чужим адресам —
это правильная защита от утечки токена. `src/secure-credentials.js` корректно
разделяет нативный Keystore и `sessionStorage` в вебе (именно session-, а не
localStorage — сознательное и верное решение).

## E. SECURITY REVIEW

**Проверено:**

- `dangerouslySetInnerHTML`, `innerHTML`, `eval`, `new Function` в
  восстановленном коде **не встречаются** — прямой XSS-поверхности нет.
- Токен сессии привязан к origin (`api-session.js`) — утечки на сторонний
  хост нет.
- Секретов в коде нет; `.env.example` содержит только пустые имена переменных
  (`OPENAI_API_KEY=`), ключи в репозиторий не попали.
- Decompression bomb — есть, P1-2.
- Path traversal при разборе архивов: имена записей используются только для
  сопоставления с регулярками (`^word/document\.xml$` и т. п.), запись на диск
  не производится — на восстановленном участке traversal не эксплуатируется.

**Не подтверждено (файлы утрачены, не делаю выводов):**
SSRF и DNS-rebinding (нет `server.mjs` — а именно там, судя по README, живёт
защита), прочность парольных записей scrypt, лимиты сессий и throttling
логина, CORS-политика шлюза, конфигурация Android-бэкапа. README заявляет
наличие SSRF-защиты и scrypt; **проверить это заявление в текущем репозитории
невозможно**, и я не принимаю его на веру.

**Отдельный риск процесса.** Два workflow с правами `contents: write`
скачивают архив по внешнему URL и **затирают содержимое ветки**
(`find . -mindepth 1 -maxdepth 1 ! -name .git -exec rm -rf {} +`), после чего
пушат результат. Проверка SHA-256 присутствует и это правильно. Но
`runtime-v410-pr-publish.yml` срабатывает на событие `pull_request` и пишет в
ветку — конструкция, которую следует убрать, а не чинить: срок действия URL
истёк, и оставлять в репозитории самозапускающийся деструктивный workflow
вредно.
